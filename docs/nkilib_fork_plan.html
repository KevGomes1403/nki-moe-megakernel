The short version

Fork aws-neuron/nki-library, don't vendor files. nkilib ships inside the neuronx-cc wheel, but AWS also publishes the whole tree publicly under Apache-2.0 — and nkilib/__init__.py contains a supported override hook: if a package providing nkilib_src is importable, nkilib replaces itself and aliases every submodule. Every existing from nkilib.core… import in both repos then resolves to your fork with zero import rewrites, and NKILIB_FORCE_BUNDLED_LIBRARY=1 flips back to stock instantly.

I found the exact commit that is byte-identical to your installed nkilib, so the fork has a verifiable zero-delta starting point. The hard part of this project is not the fork — it's that the two repos' kernels are not two versions of one library, and reconciling them is a port, not a merge.

Better than expected: these are real merges, not tree collisions

I assumed the snapshot-drop release style would make upstream merges into hostile tree-replacements. It doesn't. Your fork point 26628c5 is a direct ancestor of the 2.31_release head — git merge-base returns 26628c5 itself. So git merge upstream/2.31_release is a genuine three-way merge with a true common ancestor, and git will correctly separate your patches from AWS's changes. That is the whole benefit of forking over vendoring, and it is available immediately.

Scope correctionFork the whole tree — but for a reason you didn't state

Your instinct to clone everything is correct, though not because you need everything. The union of what both repos actually import is 37 nkilib modules; the transitive closure is 78–99 of 295 files. Seventy-three percent of the library is unreachable from your code.

The reason to take the whole tree anyway is that the override is atomic. When nkilib_src is present it displaces bundled nkilib for every consumer in the process — and NxDI and NxD import nkilib directly in 18 files (attention_base.py, gqa.py, modeling_llama.py, sampling.py, …). A partial fork would leave those importing a tree that no longer exists. Taking all 18 MB and touching only what you need is both simpler and safer than curating a subset.

The one genuine hazard of this approach

Your fork serves NxDI too. core/utils/common_types.py holds enums (QuantizationType, NormType, …) that cross the NxDI ↔ kernel boundary, and it changed 156 lines last release and 85 more in the next. If you edit those enums, NxDI breaks in ways that won't look like your change. Treat common_types.py and the core/utils/ substrate as read-only in your fork; put your patches in the kernel layer where AWS expects divergence anyway.

Both repos independently invented the same design — B's version is better

Encouragingly, the two codebases converged without coordination on the two-tier compose / jit pattern (undecorated SBUF-in/SBUF-out subkernel, thin @nki.jit entry point), and on the identical fused-slab plus two-slot prefetch ring fix for gate/up DMA fragmentation. That convergence is the strongest evidence your library vision is sound.

But repo A's kernels are not drop-in under repo B's contract, for five concrete reasons — the first two are the expensive ones:

  • Layout. B's entire composable set assumes the tp2013 H-permutation; A uses column-major [PMAX, H_free*T]. Not interconvertible without a transpose at every boundary, which defeats the no-round-trip premise.
  • Caller-visible heap discipline. A's subkernels require the caller to pop_heap in LIFO order at specific points; B's megakernel loop just chains composables. Dropping A's code in would silently corrupt SBUF.
  • Hardcoded dims. A pins _E=128, _I=192, d=PMAX; it structurally cannot express head_dim=256. B derives dims from tensor shapes.
  • Weight layout. A requires pre-transposed checkpoints; B consumes contraction-first native.
  • Allocator mode. A mandates a manual SbufManager; B defaults to auto-alloc with optional injection.

One premise in your framing turned out to be wrong, in your favour: repo B already does per-layer name prefixing. Its megakernel runs pfx = f"L{i}_" through every composable, and it does so at the caller (sbm.set_name_prefix) rather than by rewriting name= literals inside vendored files. That's the cleaner mechanism and it keeps vendored code closer to upstream — it's the approach the fork should standardise on. Repo A's 61 rewritten literals largely become unnecessary.

The residual gap is narrow and worth logging rather than fixing now: about 30 name= sites inside B's vendored attention_tkg.py are unprefixed, concentrated on block-KV-cache and debug paths the current megakernel never exercises. Enable block KV cache across two or more layers and NKI's duplicate-name checker will fire.

So the only two files that consume the vendored library are precisely the two paths with no working accuracy gate. Migrating them blind is how you get a silent numerical regression.

The mitigation is the env var

NKILIB_FORCE_BUNDLED_LIBRARY is not just a bisect tool — it's the gate you're missing. Because it toggles fork-versus-stock nkilib in-process without changing a line of your code, you can run the same kernel on the same inputs both ways and diff the output tensors directly. That gives you a kernel-level numerical regression test for exactly the paths that have no model-level one, and it costs one compile per side rather than a full logit-parity run.

Keep the prefix patch as a codemod, not a diff

The name-prefix rewrite touches 61 literals across the vendored tree — as a hand-maintained diff it will conflict on every upstream merge, forever. It is also perfectly mechanical, so it should live as a rerunnable script that re-applies the transform after each merge. Worth noting: your _vendor_meta.md maintenance protocol already instructs you to "re-run the AST scan from docs/vendor_nkilib_for_megakernel_plan.md" — and that file no longer exists. There is no docs/ directory in the repo. The tooling the protocol depends on has already decayed, which is a small but exact illustration of why the current approach doesn't hold.

PlanFive phases, run entirely inside nki-moe

The ordering change from doing this in nki-moe: the accuracy gate has to come before the vendor migration, not after, because nki-moe's two vendored-library consumers have no working gate of their own.

PHASE 0Fork, pin, and prove the no-op~half a day · no hardware
  • Fork aws-neuron/nki-library (not nki-moe — that stays your own repo). Branch from tag 2.30 = commit 26628c5 = head of 2.30_release — a tagged release head that is byte-identical to your bundled nkilib. Do not fork from main: it diverged in Dec 2025 and its snapshot commits are mislabelled (two separate commits both titled "NKI Lib 2026-04-13").
  • Add it to nki-moe as a submodule, e.g. third_party/nki-library. A submodule is a full git repo, so git merge upstream/2.31_release works inside it, and nki-moe records the exact SHA in its own history — the pinning comes for free. Set two remotes there: origin = your fork, upstream = AWS.
  • pip install -e third_party/nki-library. The submodule alone is invisible to Python; the editable install is what makes nkilib_src importable and fires the override. No import in either repo changes — the swap happens inside nkilib's own __init__.py.
  • Because the fork point is byte-identical, nothing should change — that is the test. If any behaviour shifts, stop and find out why before going further.
  • Add the pinning nki-moe has never had: constraints.txt recording neuronx-cc 2.25.3371.0, the fork commit SHA, and the venv. This absence is the root cause of "AWS ships an update and things break."
  • Stand up the inherited 341-file AWS test suite and record what passes at the fork point.
PHASE 1Build the gate you don't have~2–3 days · light hardware
  • Write an A/B harness that runs a kernel twice — once with the fork, once under NKILIB_FORCE_BUNDLED_LIBRARY=1 — and diffs output tensors. Same inputs, same seeds, exact comparison at the fork point.
  • Cover the four entry points that matter: attention_block_tkg, moe_tkg, rmsnorm_tkg, router_topk.
  • Recover repo A's deleted tests if cheap — the .pyc files under tests/*/__pycache__/ are decompilable and include test_attention_vs_hf and test_kv_cache_roundtrip, exactly the parity checks this migration needs.
  • Exit criteria: a command that tells you fork-versus-stock is numerically identical. Everything after this depends on it.
PHASE 2Strangle the vendor tree, four symbols at a time~3–5 days · moderate hardware
  • Port the name-prefix rewrite onto the fork as a codemod script plus its generated commit, not a hand-edited diff. This is the decision that determines whether merges stay cheap.
  • Re-point one entry point at a time — rmsnorm_tkg first (its vendored copy is the most decayed and carries no real patch), then router_topk, moe_tkg, attention_block_tkg. Gate each with Phase 1's harness before moving on.
  • Retire the indirect-DMA fusion files rather than porting them: default-off in production, and superseded by repo B's always-on raw-NKI version.
  • Delete nki_kernels/ when the last import is re-pointed. transformer_qwen.py is untouched throughout — your 1.76× result never moves.
PHASE 3Rehearse the upgrade you know is coming~2–4 days · moderate hardware
  • Merge ee20d3f (the already-published next release) into a throwaway branch. You face the real 284-file conflict set on your schedule instead of AWS's.
  • Re-run the codemod, then the Phase 1 harness. That loop — merge, regenerate, verify — is the maintenance process, and this is where you find out what it actually costs.
  • Whatever it costs is your recurring per-release number, and the honest input to whether this library survives long-term.
PHASE 4Bring Qwen 3.6 across onto the clean base~1–2 weeks · heavy hardware
  • Move repo B's composables into nki-moe as the top-level kernel library, organised by architecture family rather than by model — the thing that makes the next model cheap. Its three vendored/ patches become fork commits on the way in.
  • Fix the contract inconsistencies: SBUF seam defaults disagree (output_in_sbuf=True in MoE vs out_in_sb=False in GQA/DeltaNet), gqa_fused_compose returns a 3- or 5-tuple depending on a flag, and DeltaNet's name_prefix reaches only one of four callees.
  • Port repo A's genuinely unique capability onto the new contract: MX/FP8 paths, all-expert MoE, the block-KV orchestrator, cross-layer weight hoisting.
  • Decide tp2013-versus-column-major here, deliberately. It is the one blocker with no mechanical answer, and it gates how much of A's code survives.
